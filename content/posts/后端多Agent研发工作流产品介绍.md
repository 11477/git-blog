## 一、产品概述

这套多 Agent 研发工作流是一套面向团队研发场景的 AI 交付系统。它把需求澄清、产品设计、技术设计、代码开发、质量审查、测试和人工上线组织成一条可执行流程。

它要解决的不是“让 AI 多写一些代码”，而是让 AI 生成的产品文档、技术方案和代码能够在团队中被理解、审查、验证和交付。

当前产品由四部分组成：

- **四阶段流程**：产品、开发、测试、上线；
- **10 个专业 Agent**：9 个需求交付角色，外加 1 个仓库接入与 AI 能力维护角色；
- **Skills 与确定性工具**：沉淀需求澄清、代码理解、技术设计、测试、Code Review 和归档等能力；
- **人工决策机制**：项目负责人负责业务取舍、关键风险确认、真实环境验收和上线决策。

一句话概括：

> 把个人使用 AI 写代码，升级为团队可以复制、治理和审查的研发生产方式。

## 二、背景与问题

AI Coding 提升了代码生成速度，但不会自动解决研发流程中的上下游问题。随着 AI 生成能力增强，团队的主要瓶颈逐渐转移到以下环节：

![AI 编码提效后的团队交付问题](../product-introduction-diagrams/ai-coding-team-delivery-problems.png)

### 2.1 需求理解不完整

需求事实分散在需求管理平台、知识文档、附件、评论和历史系统中。AI 如果只根据一句提示词开发，容易遗漏业务边界、用户场景和验收条件。

### 2.2 产品与技术上下文割裂

PRD、原型、API、技术方案和代码由不同角色分别产生。缺少统一链路时，接口语义、权限、异常处理和发布顺序往往要到联调阶段才暴露冲突。

### 2.3 AI 容易“自己证明自己正确”

同一个 Agent 同时负责需求理解、编码、测试和验收，容易用自己的实现解释自己的需求，无法形成独立审查。

### 2.4 多 Agent 容易增加协作成本

简单增加 Agent 数量会引入重复读取、频繁转交、门禁回退和 Token 消耗。流程需要解决“什么时候用 Agent、什么时候用 Skill、什么时候直接使用脚本”的问题。

### 2.5 跨运行时交付缺少统一对象

开发、质量和测试 Agent 可能运行在不同容器中。本地文件和自然语言描述无法保证各方审查的是同一份代码。

## 三、产品定位与核心价值

### 3.1 从 AI 编码工具升级为研发交付系统

产品覆盖从需求进入到代码归档的完整过程，使 AI 不再只承担代码补全，而是参与需求澄清、方案生成、执行规划、开发验证和独立审查。

### 3.2 把团队经验变成可执行能力

将需求评审、接口设计、数据库规范、测试方法、Code Review 标准和归档要求沉淀为 Agent Instruction、Skill、模板和确定性工具，使经验能够被反复调用和持续迭代。

### 3.3 建立需求到代码的证据链

```text
需求事实
→ PRD与验收条件
→ 初步技术方案
→ HTML原型与API契约
→ 整体技术方案
→ 执行任务
→ 代码、CR与测试证据
→ 人工确认与归档
```

每一阶段都能说明输入来自哪里、输出交给谁，以及什么证据允许继续推进。

### 3.4 在效率和治理之间动态取舍

低风险修改减少不必要的规划和验证；涉及 API、数据库、缓存、权限、安全或发布策略的变更则执行完整设计、审查和专项测试。流程复杂度随变更风险调整，而不是所有需求使用同一套重流程。

## 四、四阶段业务流程

### 4.1 产品阶段：把需求变成可开发的设计基线

**调度中心**：`PM-流程总控`

主要流程：

```text
需求受理与 Grill 澄清
→ 按交付侧生成 PRD
→ 技术发现与初步技术方案
→ 按需生成单文件 HTML 原型
→ API 影响判断与契约设计
→ 整体技术方案
→ 项目负责人确认
→ 开发就绪检查与交付子 Issue
```

主要输出：

- 前端 PRD、后端 PRD或双侧 PRD；
- 《初步技术方案》；
- 可直接打开的单文件 HTML 原型；
- 《API接口总结》与 API 主制品；
- 整体技术方案；
- 经过确认的前端、后端交付子 Issue。

产品阶段的核心价值不是增加文档数量，而是在编码前关闭业务范围、接口语义和高风险技术决策。

### 4.2 开发阶段：从设计基线到可审代码

**调度中心**：`bd-开发总负责人`

主要流程：

```text
仓库准备与SHA固定
→ 开发输入校验
→ 按风险生成执行卡或纵向任务
→ 开发工程师编码与最小自检
→ 推送固定远端分支与SHA
→ 质量工程师独立Code Review
```

开发工程师负责代码实现、测试代码和最小自检；质量工程师从真实远端 Diff 出发，对需求完成度、工程规范和可测试性进行独立审查。

代码只有推送到远端 Agent 分支并固定 SHA 后，才能进入跨运行时的质量和测试环节。Agent 的自然语言说明不能代替真实代码。

### 4.3 测试阶段：验证固定版本，而不是复用开发自证

**执行角色**：`bd-测试工程师`

测试工程师针对 CR 通过后的固定远端 SHA，按适用性执行：

- 单元测试；
- 后端单边接口测试；
- 异常与失败路径测试；
- 回归测试；
- 适用的非功能性验证；
- 获得人工授权后的隔离环境集成测试和数据库验证。

测试报告必须说明测试对象、版本、范围、逐项结果、失败原因、未执行项及其影响。

Redis、MySQL、浏览器或其他环境不可用时，不把“无法执行”写成“测试通过”，也不因环境问题直接否定代码；测试 Agent 会披露缺口，并给出负责人可执行的人工测试方案。

前后端端到端测试、共享或真实环境验证及业务验收目前仍由人工完成。

### 4.4 上线阶段：当前以人工发布和决策为主

上线阶段当前主要由人执行，包括：

- 确认发布版本和窗口；
- 执行灰度或正式发布；
- 观察监控、日志和业务指标；
- 决定继续、暂停或回滚；
- 完成业务验收和需求状态收口。

Agent 可以辅助整理发布清单、风险、观测项和待回写信息，但不能宣称已经自动完成上线。

## 五、Agent 与 Skill 的协作机制

### 5.1 角色分工

| 类别 | Agent | 主要职责 |
|---|---|---|
| 产品调度 | PM-流程总控 | 需求入口、澄清、产品阶段编排与设计包确认 |
| 产品专家 | PM-技术探索专家 | 代码现状分析、初步技术方案与整体技术方案 |
| 产品专家 | PM-原型设计专家 | 基于现有前端风格生成单文件 HTML 原型 |
| 产品专家 | PM-API架构师 | API复用、组合、扩展或新增决策与契约设计 |
| 开发调度 | bd-开发总负责人 | 风险路由、阶段委派、异常收口与归档 |
| 开发执行 | bd-任务规划师 | R2/R3纵向任务、依赖与测试切入点规划 |
| 开发执行 | bd-开发工程师 | 业务代码、测试代码和最小自检 |
| 质量执行 | bd-质量工程师 | 独立 Code Review与可测试性检查 |
| 测试执行 | bd-测试工程师 | 固定SHA的单元、接口、异常、回归和专项测试 |
| 独立维护 | AI套件管理员 | 仓库AI规则、Skills和Wiki能力接入维护 |

### 5.2 为什么既需要 Agent，也需要 Skill

- **Agent**承担需要上下文理解和专业判断的工作，例如需求澄清、技术方案、接口取舍和 Code Review；
- **Skill**沉淀可复用的方法、规范和工具调用，例如需求 Grilling、代码关系查询、单元测试和数据库规范；
- **确定性工具**处理可机械校验的动作，例如仓库准备、SHA检查、路由计算和归档验证。

这种划分避免用大模型反复执行脚本能够稳定完成的工作，也避免把复杂语义判断硬编码成规则。

## 六、需求分级与质量治理

### 6.1 R0—R3风险分级

| 等级 | 典型变更 | 执行策略 |
|---|---|---|
| R0 | 注释、文案、格式、日志文字，不改变运行行为 | 无执行卡，开发、聚焦CR、最小测试 |
| R1 | 局部常量、标签、非接口注解或局部配置 | 单执行卡、聚焦CR、定向测试 |
| R2 | 局部业务逻辑、接口内部实现、错误处理或构建行为 | 标准任务、完整CR、全量适用测试 |
| R3 | API语义、数据库、缓存、消息、权限安全、生成代码或发布策略 | 多任务、完整CR、强化专项测试 |

风险等级先依据设计包判断，编码后再依据真实 Diff 复核。实际改动扩大时必须升级，不能沿用较轻路径规避验证。

### 6.2 独立质量闭环

```text
开发工程师实现
→ 质量工程师独立CR
→ 测试工程师独立测试
→ 项目负责人核验远端代码与结论
→ 归档
```

该设计主要解决 AI “自己开发、自己测试、自己宣布正确”的自证偏差。

### 6.3 人工决策边界

人工主要负责：

- 是否受理和继续需求；
- 产品范围和关键方案取舍；
- 已确认设计包是否可以进入开发；
- 端到端、真实环境和业务验收；
- 最终归档与上线决策。

使用者只需要阅读自然语言结果并用自然语言回复，不需要填写 JSON、YAML、执行键或内部状态字段。

## 七、上下文与知识体系

### 7.1 四类事实源

| 事实源 | 主要内容 |
|---|---|
| 需求管理平台 | 需求状态、优先级、排期和需求负责人 |
| 文档与知识平台 | BRD、PRD、API、技术评审和业务知识 |
| 工作流协作任务 | Agent协作、自然语言补充事实、人工确认和阶段结果 |
| Git仓库 | 代码、工程规则、远端分支、固定SHA和Wiki |

### 7.2 代码与知识查询

- 使用代码关系分析工具查找符号、调用链、字段读写路径和已有能力；
- 使用 `AGENTS.md`、`llms.txt` 和项目 Wiki 获取架构、术语和历史约束；
- 使用文档与知识平台读取业务与规范材料；
- 使用框架官方文档核验版本相关的 API 和配置语义。

下游 Agent 默认按需读取与当前任务直接相关的摘要、任务和章节，出现冲突或证据不足时再展开完整制品，以控制上下文与 Token 成本。

## 八、用户如何使用

### 8.1 发起需求

用户在根 Issue 中 mention `PM-流程总控`，至少说明：

- 为什么要做；
- 谁会使用；
- 希望实现什么结果；
- 已知的不做范围；
- 如何判断完成；
- 相关需求、文档、页面或仓库链接；
- 项目负责人。

材料不完整也可以启动。PM 会先自行读取已有事实，再通过 Grill 逐项确认真正需要人决定的问题。

### 8.2 参与确认

流程需要人工确认时，Agent 会使用可读语言说明：

- 已经完成什么；
- 当前为什么不能继续；
- 需要负责人决定什么；
- 推荐选择及其影响；
- 回复后从哪里继续。

项目负责人可以直接用自然语言回复，无需了解内部状态结构。

### 8.3 查看交付

产品阶段查看 PRD、初步技术方案、HTML 原型、API 总结和整体技术方案；开发阶段查看远端 Agent 分支、固定 SHA、代码 Diff、CR 和测试报告；上线阶段按发布与验收清单人工推进。

## 九、当前成果与评估指标

### 9.1 业务使用成果

当前流程已承接真实前后端联合需求和后端专项需求，并进入研发团队推广阶段。

当前统计：

| 指标 | 当前数据 |
|---|---:|
| 覆盖研发 RD | 3 人 |
| 进入流程的需求数 | 11 个 |
| 已承接需求数 | 7 个 |
| 需求承接率 | 约 63.6% |
| 简单后端迭代交付周期缩短 | 约 57% |

计算口径：需求承接率为 `7 ÷ 11 ≈ 63.6%`。交付周期数据来自两个同类简单后端迭代需求，平均耗时由约 `4.5 天` 缩短至约 `1.94 天`，周期缩短率为 `1 − 1.94 ÷ 4.5 ≈ 57%`。该结果用于说明已验证场景，不代表所有需求类型均能获得相同收益。

### 9.2 工程资产成果

- 完成 10 个专业 Agent 的 Prompt/Instruction 设计；
- 形成 45 个活跃 Skill 包，并复用公共平台与前端设计能力；
- 建立四阶段流程、风险分级、人工决策和异常恢复机制；
- 建立开发、Code Review、测试职责隔离；
- 建立基于远端分支和 Git SHA 的跨运行时可复现交付；
- 建立需求文档、技术制品、代码和验证证据之间的追溯关系。

工程资产的价值不只是数量，而是把团队研发经验转化为后续需求能够直接复用的执行能力。

## 十、产品边界与未来规划

### 10.1 当前明确边界

- Agent 可以完成产品设计、后端开发、独立 CR 和单边自动化测试；
- 前后端端到端测试、共享/真实环境验证和业务验收仍由人工负责；
- 上线、灰度、监控观察和回滚决策目前主要由人工推进；
- 流程不会因为材料不标准而拒绝启动，但关键业务和危险技术决策必须由项目负责人确认。

### 10.2 后续规划

- 补充前后端端到端测试能力和适用的测试环境治理；
- 持续提升开发与测试 Agent 的一次通过率；
- 建设四阶段总控 Agent，统一调度产品、开发、测试和上线阶段；
- 统计需求交付周期、承接率、一次通过率、返工次数、人工介入耗时与 Token 成本；
- 将验证有效的 Agent Prompt、Skills 和流程规则推广到更多项目与团队。

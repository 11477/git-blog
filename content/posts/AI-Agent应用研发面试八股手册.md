## 0. 面试作答总原则

### 0.1 每道技术题回答四层

1. **定义**：它是什么，解决什么问题。
2. **原理**：核心流程或关键机制是什么。
3. **权衡**：为什么选它，代价和适用边界是什么。
4. **项目**：自己在哪个场景使用过，失败过什么，如何验证。

不要只背名词。例如回答“什么是 Agent”时，不要停在“能调用工具的大模型”，而应继续说明 Agent Loop、停止条件、工具权限、失败恢复和评测。

### 0.2 项目题使用七段式

1. 用户和业务问题；
2. 原流程痛点；
3. 成功指标与约束；
4. 架构与关键技术选择；
5. 最难的一次失败及根因；
6. 量化优化结果；
7. 当前边界与下一步。

### 0.3 你的推荐自我定位

> 我主要做 AI Agent 应用工程，重点是多 Agent 工作流、知识检索、工具集成和可靠性交付。我做过一套从需求澄清、产品和技术设计，到开发、独立 Code Review、测试、人工确认和归档的多 Agent 研发工作流；也搭建过基于 OpenViking 知识库、MCP 和 DChat 的 Ultron 答疑小专家，并针对检索成本、工具接入、Embedding 故障降级和执行轨迹做过优化。

# 第一部分：Agent 基础与工作流（P0）

## 1. 什么是 AI Agent？

**回答要点**

- Agent 是由模型驱动决策、能够获取上下文、选择并调用工具、观察执行结果，并循环推进任务直至完成或退出的系统。
- 核心不是“能聊天”，而是模型参与控制工作流执行。
- 基本组成是模型、指令、工具、状态/上下文、运行循环和安全边界。

**追问**

- 只调用一次搜索接口算 Agent 吗？
- 如何判断任务完成？
- 模型说“已经执行”是否代表操作真的完成？

**项目映射**

- Ultron 小专家会选择检索工具、读取依据、组织回答并发送 DChat。
- 研发工作流包含多个 Agent 和确定性阶段路由，属于 Agentic Workflow。

## 2. Agent、Chatbot 和 Workflow 有什么区别？

**回答要点**

- Chatbot 重点是自然语言交互，不一定具备行动能力。
- Workflow 的步骤和分支主要由代码预定义，可预测、易测试。
- Agent 由模型根据当前状态动态决定下一步，更灵活但成本、延迟和不确定性更高。
- 生产系统通常是混合架构：关键流程由状态机控制，局部复杂判断交给模型。

**项目映射**

- 研发工作流的阶段顺序、人工 Gate 和归档条件应该确定化；需求澄清、任务拆解、检索和技术分析可由 Agent 动态决策。

## 3. 一个完整的 Agent Loop 是什么？

**回答要点**

```text
接收目标
→ 加载指令、状态和相关上下文
→ 模型决定回答或调用工具
→ 校验工具名、参数和权限
→ 执行工具
→ 记录 observation 和状态变化
→ 判断完成、继续、重试、降级或转人工
```

必须补充最大步骤、deadline、预算、重复动作检测和人工接管等停止条件。

## 4. 什么是 ReAct？

**回答要点**

- ReAct 将推理与行动交替进行。
- Agent 根据当前信息选择动作，通过工具获得新观察，再更新判断。
- 优点是能使用外部事实并处理中间异常；缺点是调用轮数、延迟和成本增加，可能循环。

**项目映射**

- Ultron 的“提取关键词 → grep → read → 判断依据是否充分 → 回答或升级语义检索”就是一种受约束的 ReAct 路径。

## 5. ReAct 与 Plan-and-Execute 有什么区别？

**回答要点**

- ReAct 边思考边行动，适合环境反馈频繁、计划容易变化的任务。
- Plan-and-Execute 先生成整体计划，再逐步执行，适合长任务和阶段清晰的任务。
- Plan-and-Execute 的问题是初始计划可能过早锁定，需要 replanning。
- 实际可混合：先粗计划，每一步执行后按状态调整。

## 6. Router、Supervisor、Handoff、Agents-as-tools 分别是什么？

**回答要点**

- Router：根据输入选择一个下游处理路径。
- Supervisor：中心 Agent 持续分配、检查和汇总子 Agent 工作。
- Handoff：把会话控制权和必要上下文转交给另一个 Agent。
- Agents-as-tools：主 Agent 把专业 Agent 当工具调用，控制权仍在主 Agent。

**权衡**

- Supervisor 可控但容易成为瓶颈。
- Handoff 灵活但上下文和责任边界更难管理。
- Agents-as-tools 适合专业能力清晰、输入输出契约稳定的场景。

## 7. 为什么不能一开始就使用多 Agent？

**回答要点**

- 多 Agent 会增加上下文复制、路由错误、信息丢失、重复工作、调试难度和成本。
- 如果单 Agent 加确定性工具已足够，就不应拆分。
- 只有在上下文隔离、权限隔离、专业能力差异、并行执行或团队职责确实需要时再拆。

## 8. 多 Agent 如何划分边界？

**回答要点**

- 按专业领域、数据权限、工具权限、上下文范围或生命周期阶段划分。
- 每个 Agent 都要定义输入、输出、允许动作、禁止动作、完成条件和失败返回。
- 避免按“想象中的人类岗位”无限拆分；每次拆分都应能说明收益。

**项目映射**

- 研发工作流按产品、技术探索、API、开发、CR、测试和归档划分，核心理由是职责与验收证据隔离。

## 9. 如何避免多 Agent 循环委派？

**回答要点**

- 中心状态机限制允许的下一跳。
- 记录 delegation graph 和已访问节点。
- 设置最大 handoff 次数、预算和 deadline。
- 子 Agent 不应任意创建同级 Agent。
- 返回结构化状态：成功、失败、阻塞、需补充信息，而不是自由文本暗示继续转交。

## 10. Agent 的停止条件如何设计？

**回答要点**

- 明确的最终回答或完成动作；
- 所需业务状态已经达到；
- 最大步骤、最大 Token、最大费用或 deadline；
- 连续重复动作或状态无变化；
- 权限不足、关键依赖失败；
- 风险过高或需要人工决策。

## 11. Agent 为什么会死循环？

**回答要点**

- 工具返回信息不足或错误格式；
- 没有明确完成条件；
- 模型忘记已经执行过的动作；
- 状态没有正确写回；
- 两个 Agent 相互转交；
- 错误被当成可无限重试的瞬态错误。

**解决方案**

- 动作指纹去重、状态差异检测、有限重试、错误分类、最大步骤和人工接管。

## 12. 什么是确定性工作流与 Agent 的混合架构？

**回答要点**

- 用代码/状态机控制不可绕过的阶段、权限和 Gate。
- 用模型处理需求理解、检索、规划、生成和非结构化判断。
- 模型不能自行宣布绕过测试、审批或权限检查。

**项目映射**

- 研发链路的“开发 → CR → 测试 → 人工确认 → 归档”属于确定性骨架；各阶段内部由专业 Agent 完成动态工作。

## 13. 什么是反思（Reflection）？一定有用吗？

**回答要点**

- 让模型检查先前结果、识别错误并尝试改进。
- 对复杂生成任务可能有用，但会增加成本和延迟，也可能把正确答案改坏。
- 应针对明确失败信号触发，并用评测证明收益，不能无条件循环反思。

## 14. 什么是 Evaluator-Optimizer 模式？

**回答要点**

- 一个组件生成结果，另一个按明确标准评估并提供反馈，生成器有限次修改。
- 适合标准明确、迭代能显著改善的任务。
- 必须有最大轮数和接受阈值，防止无限互评。

## 15. Agent Framework 有什么价值？什么时候自己写 Loop？

**回答要点**

- 框架提供工具调用、状态、持久化、流式、追踪、HITL 和编排抽象。
- 简单应用自己写 Loop 更透明、依赖少、便于理解。
- 长任务、复杂状态机和暂停恢复场景可使用 LangGraph 等框架。
- 面试不要只说框架名，要讲清底层状态、执行和失败模型。

# 第二部分：Prompt 与上下文工程（P0）

## 16. Prompt Engineering 和 Context Engineering 有何区别？

**回答要点**

- Prompt Engineering 侧重如何表达指令、示例、约束和输出格式。
- Context Engineering 侧重在每一步给模型选择、组织和更新正确的信息，包括系统指令、工具、记忆、检索结果和当前状态。
- Agent 可靠性很多时候不是提示词措辞问题，而是上下文缺失、冲突、过量或过期。

## 17. System、Developer、User 和 Tool 信息如何处理？

**回答要点**

- 按平台定义的指令优先级处理冲突。
- Tool 返回值原则上是数据，不应自动提升为系统指令。
- 不可信网页和文档中的文字不能覆盖高优先级规则。

## 18. 一个好的 Agent Prompt 应包含什么？

**回答要点**

- 角色和目标；
- 能力边界与禁止事项；
- 工具使用原则；
- 决策和升级条件；
- 输出契约；
- 失败、拒答和人工接管；
- 少量关键示例。

不要把所有工具参数和易变流程全部复制进 Prompt，应由工具 Schema 或 Skill 维护。

## 19. 为什么把执行流程放进 Skill，而不是全部写进 Prompt？

**回答要点**

- Skill 是可复用、可版本化的执行知识；Prompt 保持顶层角色和边界。
- 可以减少上下文占用、重复规则和两处配置不一致。
- Skill 可携带脚本、参考资料和评测，而 Prompt 不适合承载大量实现细节。

**项目映射**

- Ultron 小专家将 MCP 降级、检索顺序、DChat 发送和人工支持路径放入 `ultron-expert` Skill，Prompt 从约 200 行压缩为 51 行。

## 20. Few-shot 示例什么时候有用？

**回答要点**

- 用于展示复杂分类边界、格式和异常处理方式。
- 示例应覆盖代表性边界，避免堆砌相似 happy path。
- 示例过多会占用上下文并诱导过拟合。

## 21. 什么是 Structured Output？

**回答要点**

- 让模型输出符合给定 JSON Schema 的结构，便于程序消费。
- 比单纯提示“输出 JSON”可靠，但只能保证结构，不保证字段语义正确。
- 仍需业务校验、权限校验和错误处理。

## 22. 上下文窗口满了怎么办？

**回答要点**

- 删除无关历史；
- 对旧对话做摘要；
- 把结构化状态外置到数据库；
- 按需检索，而不是全量注入；
- 压缩工具返回；
- 给消息和制品设置优先级、版本和生命周期。

## 23. 为什么“把所有资料都塞进 Prompt”可能变差？

**回答要点**

- 噪声增加，重要信息被淹没；
- 冲突和过期内容增多；
- 延迟和成本上升；
- 长上下文并不等于模型能稳定利用每个细节。

## 24. 如何管理 Prompt 版本？

**回答要点**

- Prompt、Tool Schema、模型和 Skill 都要有版本。
- 每次变更关联离线评测结果和发布记录。
- 采用灰度、回滚和固定回归集，而不是线上直接覆盖。

## 25. 如何处理指令冲突？

**回答要点**

- 先遵守高优先级指令；
- 对同级冲突采用更具体、更新且与当前任务相关的规则；
- 无法安全判断时暂停并请求用户确认；
- 不让工具返回或检索文档改变系统安全边界。

# 第三部分：Tool Calling、MCP 与 Skills（P0）

## 26. Function Calling 的完整流程是什么？

**回答要点**

1. 应用向模型提供工具名称、描述和参数 Schema；
2. 模型返回工具选择和参数；
3. Runtime 校验参数与权限；
4. 应用真正执行函数；
5. 把结果作为 Tool Message 返回模型；
6. 模型继续决策或生成最终答案。

模型生成调用意图不等于工具已经执行。

## 27. 如何设计高质量工具？

**回答要点**

- 名称清晰、动词明确；
- 描述写清何时用和何时不用；
- 参数尽量结构化，使用枚举和必填字段；
- 返回稳定、简洁、可判错；
- 明确副作用、幂等性、权限和错误类型；
- 粒度既不能过粗，也不能碎成大量相似工具。

## 28. 工具太多会发生什么？

**回答要点**

- Schema 占用上下文；
- 相似工具增加误选；
- 规划空间变大；
- 权限和版本管理更复杂。

可采用工具分组、按场景动态装载和工具检索。

## 29. 工具参数为什么必须再次校验？

**回答要点**

- 模型输出不可信；即使结构正确，值也可能越权或危险。
- 需要 Schema 校验、业务规则、ACL、资源归属、长度范围和注入防护。

## 30. 工具调用失败如何分类？

**回答要点**

- 参数错误：让模型修正有限次数；
- 认证/权限错误：不要盲目重试；
- 限流/超时/5xx：可退避重试或 fallback；
- 业务冲突：查询状态或请求用户决策；
- 结果不确定：避免重复副作用，先查执行状态；
- 永久失败：降级或转人工。

## 31. 为什么重试必须考虑幂等？

**回答要点**

- 请求超时不代表服务端没执行。
- 对发信、付款、删改等副作用操作直接重试可能重复执行。
- 使用 idempotency key、操作状态查询、唯一约束、事务、Outbox 或补偿动作。

## 32. 什么是 MCP？

**回答要点**

- Model Context Protocol 是连接 LLM 应用与外部数据、工具和上下文的标准协议。
- 它标准化能力发现、调用、生命周期和消息格式，降低每个 Agent 单独适配外部系统的成本。
- MCP 不替代业务 REST API，MCP Server 可以在业务 API 之上提供适合模型调用的接口。

## 33. MCP 中 Host、Client、Server 分别是什么？

**回答要点**

- Host：承载模型应用、管理权限与多个连接。
- Client：Host 内连接某一个 Server 的协议组件。
- Server：提供 Tools、Resources、Prompts 等能力。
- Host 应维护用户控制和安全边界，不应把权限判断交给模型。

## 34. MCP 的 Tools、Resources、Prompts 有什么区别？

**回答要点**

- Tools：模型可以调用的可执行能力，可能产生副作用。
- Resources：可读取的上下文或数据。
- Prompts：可复用的提示模板或工作流入口。

## 35. MCP 为什么使用 JSON-RPC？

**回答要点**

- 提供统一的请求、响应和通知语义；
- 支持 capability negotiation、错误、取消和进度；
- 可运行在不同传输之上。

## 36. stdio 和 HTTP 传输怎么选？

**回答要点**

- stdio 适合本机子进程、开发工具和单用户环境，部署简单。
- HTTP 适合远程、多用户和服务化场景，需要认证、会话、网络和横向扩展设计。

## 37. MCP 与普通 SDK 集成相比有什么优势和代价？

**回答要点**

- 优势：标准化发现和调用、复用生态、减少 Agent 与具体服务耦合。
- 代价：增加协议层、版本兼容、权限、连接和调试复杂度。
- 内部稳定的单一集成不一定必须使用 MCP。

## 38. MCP Server 的 Tool 如何做安全设计？

**回答要点**

- 最小权限；
- 读写分离；
- 输入校验；
- 用户委托授权；
- 高风险动作审批；
- 审计；
- 输出视为不可信内容；
- 防止 token 透传、跨租户访问和凭证泄漏。

## 39. Skills 与 Tools 的区别是什么？

**回答要点**

- Tool 是可执行能力；Skill 是指导 Agent 如何完成某类任务的可复用流程知识。
- Skill 可以组合多个工具、规则、参考资料和验证脚本。
- Tool 更像“手和 API”，Skill 更像“做事的方法”。

## 40. 原生 MCP 工具没有注入时怎么办？

**回答要点**

- 先使用已批准且确定的连接方式或 CLI 适配器。
- 不应让 Agent 临时手写协议、反复猜 session 和参数。
- 工具接入失败应与业务检索失败区分，记录为不同错误类型。

**项目映射**

- Ultron 轨迹中原生 OpenViking 工具缺失后出现大量 MCP 协议探测，后来通过 Skill 固化为直接使用 `mcporter` 的降级路径。

# 第四部分：RAG 与知识 Agent（P0）

## 41. 什么是 RAG？

**回答要点**

- RAG 在生成前从外部知识源检索相关内容，将证据加入上下文再回答。
- 适合知识频繁变化、需要引用、不能完全依赖模型参数记忆的场景。
- RAG 不会自动消除幻觉，检索、上下文组织和生成都可能出错。

## 42. RAG 的完整链路是什么？

```text
数据采集 → 解析清洗 → 切分 → Embedding → 建索引
用户查询 → 查询改写 → 召回 → 过滤 → 重排
→ 上下文拼装 → 生成 → 引用/拒答 → 评测反馈
```

## 43. Chunk Size 和 Overlap 如何选择？

**回答要点**

- 小块定位精确，但语义可能不完整；大块上下文完整，但噪声和成本高。
- 根据文档结构、问题粒度和模型窗口实验选择。
- 优先结构化切分：标题、段落、表格、代码函数，而不是只按字符数。

## 44. BM25 和向量检索有什么区别？

**回答要点**

- BM25 基于词项匹配，对错误码、函数名、配置项和专有词很强。
- 向量检索对同义表达、口语改写和语义相关更强。
- 向量检索依赖 Embedding，可能召回“语义相似但事实不相关”的内容。

## 45. 什么是 Hybrid Search？

**回答要点**

- 同时使用稀疏检索和稠密检索，再融合分数或结果。
- 兼顾精确词与语义匹配。
- 需要处理两类分数不可直接比较、候选去重和融合权重。

## 46. Retriever 和 Reranker 有什么区别？

**回答要点**

- Retriever 从大规模语料快速找候选，强调召回与速度。
- Reranker 对少量候选做更精细的 query-document 相关性判断，强调排序精度。
- Cross-Encoder 通常更准但更慢，适合候选集二次排序。

## 47. 为什么 Ultron 小专家选择 grep 优先？

**回答要点**

- 用户问题常包含 DiSF、Odin、cuuid、错误码和配置字段等高区分度词。
- 词法检索便宜、快、可解释，不需要 Embedding 和 Rerank。
- grep 命中且证据充分就结束；口语化或无明确术语时再升级 find/search。
- 这是成本和召回质量的路由策略，不代表词法检索永远优于语义检索。

## 48. Embedding 是什么？

**回答要点**

- 把文本映射为稠密向量，使语义相近的文本在向量空间接近。
- 检索时比较查询向量与文档向量的相似度。
- 模型、维度、归一化、语言和领域都会影响效果。

## 49. 余弦相似度、点积和 L2 有何区别？

**回答要点**

- 余弦关注方向；
- 点积同时受方向和模长影响；
- L2 衡量欧氏距离。
- 向量归一化后，余弦和点积排序可等价；必须与 Embedding 模型和索引配置匹配。

## 50. HNSW 的基本思想是什么？

**回答要点**

- 构建多层近邻图，高层做长距离跳转，低层做局部精细搜索。
- 用近似换速度和内存，关键参数影响构建成本、查询延迟和召回率。

## 51. Query Rewrite 有什么作用？

**回答要点**

- 消除指代、补全上下文、标准化术语、拆分复杂问题。
- 风险是改写偏离原意；应保留原查询，并用评测验证。

## 52. Multi-query 和 HyDE 是什么？

**回答要点**

- Multi-query 生成多个查询表达并合并召回，提高覆盖。
- HyDE 先生成假设性答案/文档，再用其向量检索。
- 都会增加成本，并可能引入错误语义，适合召回困难时按需启用。

## 53. RAG 中 Metadata Filter 的作用是什么？

**回答要点**

- 按租户、权限、时间、文档类型、产品版本等先过滤检索范围。
- 权限过滤必须由后端执行，不能只在 Prompt 中要求模型保密。

## 54. 如何让 RAG 回答可追溯？

**回答要点**

- 保留文档 ID、版本、段落位置和链接；
- 回答中的关键结论绑定证据；
- 区分文档事实、合理推断和排障建议；
- 证据不足时拒答或转人工。

## 55. RAG 如何评测？

**回答要点**

- 检索层：Recall@K、Precision@K、MRR、nDCG。
- 生成层：正确性、完整性、faithfulness、引用准确性、拒答准确性。
- 系统层：任务成功率、延迟、成本、人工转交率。
- 必须把检索失败和生成失败分开定位。

## 56. 召回文档正确但答案仍错，怎么排查？

**回答要点**

- 文档解析是否损坏；
- 关键段落是否在送入模型的 chunk；
- 排序和截断是否丢掉关键信息；
- Prompt 是否要求基于证据；
- 模型是否混入参数记忆；
- 引用是否与结论真正对应。

## 57. RAG 找不到答案时怎么办？

**回答要点**

- 尝试术语提取、查询改写、词法/语义切换和受限的多跳检索；
- 达到预算后明确说明证据不足；
- 给出人工支持路径和需要补充的材料；
- 将失败样本进入评测集和知识缺口队列。

## 58. Agentic RAG 与普通 RAG 有何区别？

**回答要点**

- 普通 RAG 通常固定执行一次检索和生成。
- Agentic RAG 由模型决定是否检索、检索哪个数据源、是否改写、继续多跳或停止。
- 灵活性更强，但延迟、成本、循环和不可控性也增加。

## 59. 长上下文可以替代 RAG 吗？

**回答要点**

- 长上下文适合资料规模有限且需要全局关系的任务。
- RAG 适合大规模、动态更新、权限隔离和需要精准引用的知识。
- 长上下文仍有成本、延迟、噪声和有效利用问题，两者可组合。

## 60. 如何处理知识库更新和删除？

**回答要点**

- 增量解析和索引；
- 文档/Chunk 版本与内容哈希；
- 删除传播和缓存失效；
- 旧版本引用可追溯；
- 评测集覆盖版本变化。

# 第五部分：状态、记忆与长任务（P1）

## 61. Context、State、Memory 和 Checkpoint 有何区别？

**回答要点**

- Context：当前模型调用实际看到的信息。
- State：工作流当前的结构化业务状态。
- Memory：跨步骤或跨会话保留、未来可能复用的信息。
- Checkpoint：某个执行时刻持久化的状态快照，用于恢复、审计或重放。

## 62. 短期记忆和长期记忆如何划分？

**回答要点**

- 短期记忆服务当前会话/任务，例如消息、当前计划和临时结果。
- 长期记忆跨会话保存用户偏好、稳定事实或历史经验。
- 长期记忆需要写入规则、过期、删除、冲突和权限治理。

## 63. 为什么聊天记录不等于记忆？

**回答要点**

- 全量历史噪声大、成本高、可能过期和泄漏隐私。
- 真正的记忆应经过选择、结构化、版本化和生命周期管理。

## 64. Checkpoint 应保存什么？

**回答要点**

- Run/Thread ID；
- 当前节点和状态；
- 已完成工具调用及结果引用；
- 待执行计划；
- Prompt/模型/工具版本；
- 预算和 deadline；
- 审批状态；
- 幂等键和副作用执行状态。

## 65. 如何恢复中断任务？

**回答要点**

- 从最后一个一致 checkpoint 加载状态；
- 对已执行副作用查询真实状态，不盲目重放；
- 后续节点必须可重入；
- 记录恢复原因、版本变化和审计事件。

## 66. Human-in-the-loop 如何与 Checkpoint 配合？

**回答要点**

- 在高风险工具执行前暂停并保存状态；
- 向审批者展示动作、参数、影响、证据和风险；
- 审批后从同一 Run 恢复；
- 审批前可能执行的步骤必须幂等。

## 67. 多 Agent 如何共享状态？

**回答要点**

- 使用结构化共享状态或制品引用，不要复制全部聊天历史。
- 定义字段所有权、版本、并发控制和可见范围。
- 对大文件传 URI/Artifact ID，而不是反复放入 Prompt。

## 68. 如何防止记忆污染？

**回答要点**

- 不可信输入不能直接写长期记忆；
- 写入需要来源、置信度、用户范围和审核策略；
- 共享记忆默认只读或受控写；
- 支持删除、回滚和冲突解决。

# 第六部分：评测、Trace 与可观测性（P0）

## 69. 为什么 Agent 不能只评最终答案？

**回答要点**

- 同一个正确答案可能通过危险、昂贵或不可复现的路径得到。
- 应同时评估工具选择、参数、证据、轨迹、步骤数、副作用和安全性。

## 70. Agent 评测有哪些层次？

**回答要点**

- 单步：工具是否选对、参数是否正确；
- 轨迹：是否走了合理路径，有无无效调用；
- 最终结果：任务是否完成、答案是否正确；
- 系统：延迟、成本、稳定性和安全。

## 71. 如何构造评测集？

**回答要点**

- 真实用户问题；
- 线上失败案例；
- 正常、边界、权限、工具故障和注入案例；
- 少量合成扩充；
- 标注期望结果、允许路径和禁止行为；
- 固定版本并持续加入新失败样本。

## 72. 规则评分、LLM-as-Judge 和人工评分怎么选？

**回答要点**

- 规则评分稳定、便宜，适合结构、工具和确定性事实。
- LLM Judge 灵活，适合语义质量，但有随机性和偏差。
- 人工评分质量高但昂贵。
- 实际组合使用，并用人工 Gold Set 校准 Judge。

## 73. LLM-as-Judge 有哪些偏差？

**回答要点**

- 位置偏差、长度偏好、自我偏好、风格偏好；
- 评分不稳定；
- 可能缺乏领域知识；
- 容易被待评分内容注入。

## 74. Trace 应记录什么？

**回答要点**

- Run、Thread、Step ID；
- Prompt、模型和 Tool 版本；
- 工具名、参数摘要、结果状态；
- 状态转移；
- Token、耗时、费用；
- 重试、错误和降级；
- 审批与用户反馈；
- 敏感信息需脱敏。

## 75. 如何利用 Trace 定位问题？

**回答要点**

- 先按失败类别聚类：模型、检索、工具、权限、编排、基础设施。
- 找到第一个偏离预期的步骤，而不是只看最后一句话。
- 对照成功轨迹和失败轨迹，建立最小复现与回归用例。

**项目映射**

- Ultron 运行轨迹中只有 2 步有效检索，却出现 18 次协议探测、7 次工具发现和 5 次无关 Issue 操作；通过 Trace 将问题定位为工具注入和 Skill 边界不清。

## 76. 如何评测 Ultron 小专家？

**回答要点**

- 建立问题—标准证据—期望结论数据集；
- 评估检索命中率、回答正确性、引用准确性和正确拒答；
- 模拟 Embedding 401、MCP 不可用、无权限和文档缺失；
- 统计平均工具调用数、p95 延迟、Token/任务成本和人工转交率。

## 77. 如何评测多 Agent 研发工作流？

**回答要点**

- 最终交付是否满足需求；
- 阶段制品是否完整、一致；
- 是否绕过 CR、测试或人工 Gate；
- 返工次数和错误路由；
- 远端代码证据与评审对象是否一致；
- 人工介入时间、交付周期和产出采纳率。

## 78. Offline Eval 与 Online Eval 有何区别？

**回答要点**

- Offline 用固定数据集做发布前比较和回归。
- Online 基于真实流量监控质量、异常和用户反馈。
- 线上失败应脱敏后回流离线集，修复后先离线验证再灰度。

## 79. 如何避免只对评测集过拟合？

**回答要点**

- 保留独立测试集；
- 按问题类型和时间切分；
- 加入新鲜真实流量；
- 不只调 Prompt，也检查工具、数据和系统问题；
- 观察线上业务指标。

## 80. Agent 的核心线上指标有哪些？

**回答要点**

- 任务成功率；
- 正确工具/参数率；
- 人工接管率；
- p50/p95/p99 延迟；
- 平均步骤和重试；
- 单次成功任务成本；
- 安全违规率；
- 用户满意度。

# 第七部分：安全、权限与可靠性（P0）

## 81. Prompt Injection 和 Jailbreak 有何区别？

**回答要点**

- Prompt Injection 通过输入或外部内容改变 Agent 行为，包括间接注入。
- Jailbreak 通常指绕过模型安全限制的提示策略。
- 对 Agent 而言，间接注入更危险，因为网页、邮件和文档可能诱导调用真实工具。

## 82. 为什么 System Prompt 不是安全边界？

**回答要点**

- 模型可能误解、被注入或生成错误参数。
- 权限、资源范围、输入校验和审批必须由确定性代码执行。

## 83. 什么是最小权限？

**回答要点**

- Agent 只获得当前任务必需的工具、数据和时间范围。
- 读写工具分离；用户权限不自动扩大为 Agent 服务权限。
- 高风险权限短期化、可撤销、可审计。

## 84. 哪些动作应当 HITL？

**回答要点**

- 付款、删除、发信、外部发布、生产变更；
- 大范围或不可逆操作；
- 权限提升和敏感数据导出；
- 低置信度但影响重大的决策。

## 85. 如何安全执行代码？

**回答要点**

- 容器或 VM 隔离；
- 文件系统和网络 egress 限制；
- CPU、内存、时间和进程数配额；
- 凭证不进入沙箱；
- 命令 allowlist/denylist 只是辅助；
- 产物扫描和完整审计。

## 86. 如何防止 Agent 越权查询知识库？

**回答要点**

- 检索前按用户身份和租户做 ACL Filter；
- 结果返回前再次授权；
- 缓存和向量索引也要按权限隔离；
- 不能依赖模型自觉不展示内容。

## 87. 如何处理不可信工具返回？

**回答要点**

- 把返回内容当数据，不当高优先级指令；
- 进行结构、长度和内容清洗；
- 不允许工具返回直接触发另一个高风险动作；
- 必要时隔离引用与指令通道。

## 88. 什么是审计链？

**回答要点**

- 谁以谁的身份，在何时通过哪个 Agent 调用了哪个工具；
- 使用了什么参数和授权；
- 结果、状态变化和审批人是什么；
- 支持追责、复盘和合规检查。

# 第八部分：后端与计算机基础（P0）

## 89. Python 的 GIL 是什么？

**回答要点**

- CPython 中同一进程通常只有一个线程执行 Python 字节码。
- I/O 密集任务仍可用线程或 asyncio；CPU 密集任务可用多进程、原生扩展或外部计算服务。

## 90. 线程、进程和协程怎么选？

**回答要点**

- 线程：I/O 并发、共享内存方便，但有同步问题。
- 进程：CPU 密集和隔离，通信成本更高。
- 协程：大量 I/O 任务，高并发低开销，但不能阻塞事件循环。

## 91. asyncio 事件循环如何工作？

**回答要点**

- 协程在等待 I/O 时主动让出执行权；事件循环在事件就绪后恢复任务。
- 需要处理 timeout、cancel、Semaphore、连接池和异常传播。

## 92. SSE 和 WebSocket 如何选择？

**回答要点**

- SSE 是服务端到客户端的单向事件流，适合 LLM Token 和进度流式返回，基于 HTTP、重连简单。
- WebSocket 双向通信，适合实时控制和频繁交互，但连接治理更复杂。

## 93. TCP 重传与业务重试有什么区别？

**回答要点**

- TCP 保证字节传输，不理解业务是否执行。
- 业务超时后重试可能让同一副作用执行两次，因此需要幂等和状态查询。

## 94. 数据库事务的 ACID 是什么？

**回答要点**

- 原子性、一致性、隔离性、持久性。
- 面试需继续说明隔离级别、脏读、不可重复读、幻读和 MVCC。

## 95. 如何设计 Agent Run 数据表？

**回答要点**

- Run：目标、状态、用户/租户、版本、预算、时间；
- Step：节点、输入输出引用、状态、耗时和错误；
- Tool Call：工具、参数摘要、幂等键、结果；
- Message/Artifact/Checkpoint 分表或对象存储；
- 事件表用于审计和流式恢复。

## 96. Redis 在 Agent 系统中能做什么？

**回答要点**

- 缓存、限流、短期状态、分布式锁、事件流和任务队列。
- 关键状态不能只依赖易失缓存；锁需要过期和 owner 校验。

## 97. 缓存穿透、击穿和雪崩是什么？

**回答要点**

- 穿透：查询不存在数据绕过缓存；可用空值缓存、布隆过滤器。
- 击穿：热点 Key 过期瞬间大量回源；可用互斥更新、逻辑过期。
- 雪崩：大量 Key 同时过期或缓存故障；可加随机过期、多级缓存和降级。

## 98. 消息队列为什么适合长任务？

**回答要点**

- 解耦请求与执行、削峰、重试和异步扩展。
- 需要消费幂等、可见性超时、死信队列、顺序和状态查询。

## 99. 至多一次、至少一次和恰好一次是什么？

**回答要点**

- 至多一次可能丢，不重复；
- 至少一次不丢但可能重复；
- 端到端恰好一次通常需要消息系统与业务幂等/事务共同保证，不能只靠一句配置。

## 100. 常见限流算法有哪些？

**回答要点**

- 固定窗口简单但边界突刺；
- 滑动窗口更平滑；
- 漏桶稳定输出；
- 令牌桶允许一定突发。

Agent 系统还应按用户、租户、模型 RPM/TPM 和工具分别限额。

## 101. timeout、retry、circuit breaker、bulkhead 分别解决什么？

**回答要点**

- Timeout：限制等待时间；
- Retry：恢复瞬态故障；
- Circuit Breaker：依赖持续失败时快速失败；
- Bulkhead：隔离资源池，防止一个依赖拖垮全局。

## 102. 什么是背压？

**回答要点**

- 下游处理不过来时，上游必须减速、排队、拒绝或降级。
- 可用有界队列、Semaphore、租户配额、429、动态并发和取消传播。

## 103. 如何保证多租户隔离？

**回答要点**

- 身份、数据、索引、缓存、凭证、队列和计算资源都要带租户边界。
- 查询必须从认证上下文获取 tenant ID，不能相信模型生成的 tenant 参数。

## 104. Agent 长任务如何取消？

**回答要点**

- Run 状态设为 cancel requested；
- 向执行节点传播 cancellation token；
- 正在运行的外部工具尽力取消；
- 已完成副作用不回滚时要明确展示；
- 保存最终状态和审计事件。

## 105. 如何做模型网关？

**回答要点**

- 统一认证、模型路由、限流、重试、Fallback、日志、成本和敏感信息处理。
- 路由依据能力、延迟、价格、上下文长度、地域和可用性。
- 不能对有副作用的整条 Agent Loop 进行无脑重放。

## 106. 常见算法题准备范围

必须会手写并分析复杂度：

- 哈希与两数之和；
- LRU Cache；
- 堆与 Top-K；
- 二叉树遍历；
- BFS/DFS；
- 滑动窗口；
- 链表；
- 并查集；
- 最短路径。

规划方向额外准备 A*、Beam Search 和 MCTS 的基本思想。

# 第九部分：LLM 与 Transformer 基础（应用岗深度）

## 107. Transformer 的核心结构是什么？

**回答要点**

- Self-Attention、前馈网络、残差连接、归一化和位置表示。
- 自回归语言模型根据前文预测下一个 Token。

## 108. Q、K、V 分别是什么？

**回答要点**

- Query 表示当前位置要寻找什么；
- Key 表示每个位置可被匹配的特征；
- Value 是匹配后聚合的信息；
- 权重通常由 `softmax(QKᵀ / sqrt(d_k))` 得到。

## 109. 为什么除以 `sqrt(d_k)`？

**回答要点**

- 维度增大时点积方差变大，softmax 容易饱和，梯度变小。
- 缩放有助于保持数值稳定。

## 110. Multi-Head Attention 的作用是什么？

**回答要点**

- 让模型在不同表示子空间学习不同关系。
- 多头结果拼接后再投影。

## 111. MHA、MQA、GQA 有何区别？

**回答要点**

- MHA 每个 Query 头有独立 K/V；
- MQA 多个 Query 头共享一组 K/V，KV Cache 更省；
- GQA 多组 Query 头共享若干组 K/V，在质量和推理效率之间折中。

## 112. 为什么 Attention 通常是 O(n²)？

**回答要点**

- 序列中每个位置与所有位置计算注意力分数，形成 n×n 矩阵。
- 长上下文还会增加 KV Cache、首 Token 延迟和显存压力。

## 113. 什么是 KV Cache？

**回答要点**

- 自回归解码时缓存历史 Token 的 Key/Value，避免每生成一个 Token 都重新计算全部历史。
- 代价是显存随上下文长度、batch 和层数增长。

## 114. Prefill 和 Decode 有什么区别？

**回答要点**

- Prefill 并行处理输入上下文，计算密集；
- Decode 逐 Token 生成，常受内存带宽和 KV Cache 影响。

## 115. temperature 和 top-p 有什么作用？

**回答要点**

- Temperature 调整概率分布尖锐程度；
- top-p 只从累计概率达到阈值的候选中采样；
- 工具调用和结构化任务通常使用较低随机性，但不能靠 temperature 保证业务正确。

## 116. Tokenization 为什么影响 Agent？

**回答要点**

- 影响上下文长度、费用、延迟和截断。
- 代码、中文和大型 Tool Schema 的 Token 效率不同。
- 工具描述和重复历史可能消耗大量输入 Token。

## 117. Prompt、RAG 和 Fine-tuning 怎么选？

**回答要点**

- Prompt：快速定义行为和规则；
- RAG：动态知识、引用和权限；
- Fine-tuning：稳定风格、行为模式或领域能力；
- 可以组合，选择依据是问题属于知识、行为还是基础能力。

## 118. SFT、RLHF、DPO 分别是什么？

**回答要点**

- SFT 用高质量输入输出示例做监督微调。
- RLHF 通常通过偏好数据、奖励模型和策略优化对齐行为。
- DPO 直接使用 chosen/rejected 偏好对优化策略，相比 PPO 型流程更简单。

应用岗理解目标、数据和适用性即可；算法岗需进一步推导和实践。

## 119. LoRA 为什么省资源？

**回答要点**

- 冻结原模型权重，只训练插入的低秩矩阵。
- 可显著减少可训练参数和优化器状态，但不代表推理和数据质量问题自动解决。

## 120. 大模型幻觉的原因和治理方式是什么？

**回答要点**

- 自回归目标优化的是合理的下一个 Token，不是真实性保证。
- 知识缺失、上下文噪声、错误检索和提示诱导都会导致幻觉。
- 使用检索、工具、引用、结构校验、拒答、评测和人工接管组合治理。

# 第十一部分：项目一专项拷打——多 Agent 研发工作流

## 126. 请用三分钟介绍这个项目

**推荐结构**

> 这个项目解决的是一句模糊需求直接交给 AI 编码后，容易出现上下文不完整、职责混乱、代码不可验证和交付不可追溯的问题。我把现有研发流程改造成一套 Spec-driven 多 Agent 工作流，覆盖需求澄清、产品/技术/API 设计、任务规划、开发、独立 Code Review、测试、人工确认和归档。确定性状态机保证关键阶段不能绕过，Agent 负责各阶段的非结构化分析和执行；Skills 封装可复用流程，远端 Git SHA 和制品引用保证多个 Agent 操作同一个可验证对象。项目重点不是 Agent 数量，而是职责隔离、上下文交接、失败恢复和证据化交付。

随后补充真实规模、指标和个人负责模块。

## 127. 为什么要做多 Agent，单 Agent 不行吗？

**回答要点**

- 单 Agent 可以完成简单链路，但长上下文中角色、权限和验收标准容易混杂。
- 开发者自评代码容易产生确认偏差；CR 和测试独立能提供不同证据。
- 不是每一步都拆 Agent，只有职责、权限、上下文和验收标准明显不同的阶段才拆。

## 128. 为什么是 Spec-driven，而不是直接 Coding？

**回答要点**

- 需求、接口、约束和验收标准先形成版本化制品；
- 开发和验证基于同一事实来源；
- 减少反复从聊天记录恢复上下文；
- 便于回溯需求变更与代码差异。

## 129. 与 OpenSpec 有什么区别？

**回答要点**

- 思想上都强调先明确规格再编码。
- 你的系统不只生成 Spec，而是覆盖产品、技术、API、开发、CR、测试和人工确认的完整交付链。
- 沿用组织已有 BRD/PRD/API/技术方案制品，降低迁移成本。

## 130. Agent 之间如何传递上下文？

**回答要点**

- 传结构化状态和版本化制品引用，而不是全量聊天历史。
- 每一阶段声明输入制品、输出制品、版本和完成状态。
- 大文件用 URI、仓库路径或 Artifact ID。

## 131. 为什么需要独立 CR 和测试 Agent？

**回答要点**

- CR 关注规范、设计一致性和可测试性；测试关注行为是否满足需求和风险。
- 两者必须基于同一远端 SHA。
- 测试后代码变化需重新做聚焦 CR 和受影响范围复测。

## 132. 如何保证多个 Agent 看的是同一份代码？

**回答要点**

- 以远端分支和 Git SHA 作为不可歧义的交付对象。
- CR、测试和归档记录同一个 SHA。
- 本地未推送修改不能作为正式评审证据。

## 133. 风险分级如何影响流程？

准备说明自己的 R0—R3 定义、评估维度和差异。至少覆盖：

- 影响范围；
- 数据/权限风险；
- 接口兼容；
- 回滚难度；
- 测试深度和人工 Gate。

不要声称低风险可以绕过基本 CR 和测试，除非真实规则如此。

## 134. 某个 Agent 失败后如何返工？

**回答要点**

- 错误分类为实现问题、制品问题、需求决策问题或环境阻塞。
- 默认回到最近能修复根因的节点，不从头重跑。
- 只重开受影响决策和制品。
- 记录返工原因、版本变化和重新验证范围。

## 135. 如何防止 Agent 自己宣布“测试通过”？

**回答要点**

- 测试结果必须来自确定性命令、CI 或测试工具。
- 使用标准状态，如 PASSED、FAILED、BLOCKED_ENV、NOT_EXECUTED、NOT_APPLICABLE。
- 没有运行证据不能写通过。

## 136. Human Gate 放在哪里？为什么？

**回答要点**

- 需求关键决策、重大技术方案、高风险操作和最终交付确认。
- Gate 太多会拖慢流程，应把机械验证自动化，只保留高影响判断。

## 137. Skills 为什么这么多，如何避免失控？

**回答要点**

- Skill 按稳定能力和单一职责拆分，不按每个临时任务创建。
- 建立 Agent—Skill 映射、触发条件、所有者、版本和废弃流程。
- 识别重复或孤立 Skill，合并能力并清理旧入口。

## 138. 这个项目最大的技术难点是什么？

可从以下选一个最有证据的回答：

- 多 Agent 上下文一致性；
- 确定性 Gate 与模型灵活性的平衡；
- CR/测试基于同一 Git SHA；
- 返工只重开受影响节点；
- Agent 与 Skills 的职责治理。

必须讲一个具体失败案例，不能只说“流程复杂”。

## 139. 如何评估工作流是否真的提效？

**回答要点**

- 交付周期、人工介入时间、返工次数；
- Issue 吞吐量和产出采纳率；
- 一次通过率、CR/测试发现问题；
- Agent 成功率和单位交付成本。

在没有真实数据时明确写 `[待补数据]`，不要编数字。

准备精确回答：

# 第十二部分：项目二专项拷打——Ultron 小专家

## 141. 请用三分钟介绍 Ultron 小专家

**推荐结构**

> Ultron 小专家是面向内部平台用户的知识答疑 Agent。它接收 DChat 群聊问题，通过 MCP 访问 OpenViking 中的 Ultron 文档，检索可靠依据后组织答案，并在群里 @提问人回复。为了控制成本和提升确定性，我根据问题特征采用词法检索优先、语义检索兜底；同时针对 Embedding 401、工具未注入、重复 MCP 探测和无关 Issue 操作设计了降级和边界。系统强调有依据回答、证据不足转人工，而不是让模型自由发挥。

## 142. 为什么不用普通 FAQ Bot？

**回答要点**

- 问题包含自然语言改写、错误场景和多文档证据；
- Agent 需要选择检索方式、读取文档、判断证据充分性和决定拒答/转人工；
- 对固定高频问题仍可以缓存或使用确定性 FAQ 路径。

## 143. 完整调用链是什么？

```text
DChat事件
→ 提取问题、username、channel_id
→ 调用 ultron-expert Skill
→ OpenViking grep/read；必要时 find/search
→ 证据判断与答案生成
→ 调用发送 Skill
→ @用户回复一次
→ 结束
```

## 144. 为什么 grep 优先、Embedding 兜底？

参见第 47 题。回答时加入实际场景：DiSF、Odin、cuuid 等专有词非常适合词法召回；口语和同义表达才升级语义检索。

## 145. Embedding 服务 401 时为什么不能回答“知识库没有答案”？

**回答要点**

- 401 是检索通道认证失败，不代表数据不存在。
- 应把“工具/基础设施失败”和“检索无结果”建模为不同状态。
- 可以降级到不依赖 Embedding 的 grep/list/read；仍失败才说明暂时无法可靠回答。

## 146. 原生 MCP 工具没有注入时发生了什么？

**回答要点**

- Agent 不知道确定入口，开始手写 MCP initialize、SSE/session 和参数探测。
- 产生大量无效调用和延迟。
- 后来在 Skill 中固化：原生工具存在直接调用，否则立即使用批准的 `mcporter` 路径，禁止临时实现协议客户端。

## 147. 如何证明优化有效？

**回答要点**

- 优化前 Trace：18 次协议探测、7 次接入发现、5 次无关 Issue 操作，真正有效检索只有 2 步。
- 优化后的目标路径：启动 Skill → grep → read → DChat send → 结束。
- 还需补真实复测数据：平均调用数、p95 延迟和成功率 `[待补数据]`。

## 148. 为什么 Prompt 和 Skill 要拆开？

参见第 19 题。结合项目说明 Prompt 只保留角色、服务范围和顶层边界，检索与发送细节由 Skill 作为单一事实来源维护。

## 149. 如何保证回答不是幻觉？

**回答要点**

- 关键结论必须来自读取到的文档；
- 明确区分文档事实和排障建议；
- 给出可点击参考文档；
- 没有证据时拒答或转人工；
- 用固定问题集评估引用与结论一致性。

## 150. 如何处理回答过于简略与过度推断的矛盾？

**回答要点**

- 按问题类型选择输出结构：简单事实简洁，故障排查提供结论、步骤、仍失败处理和参考文档。
- 详细不等于可以编造；未经文档支持的错误码含义必须标为推断或不输出。

## 151. DChat 重复发送如何防止？

**回答要点**

- 事件 ID 或消息 ID 作为幂等键；
- 发送记录落库或缓存；
- 成功后结束，不让多个节点各自发送；
- 重试前查询状态；
- Mention 格式由发送层统一处理。

## 152. OpenViking 出现两个 MCP 配置为什么有问题？

**回答要点**

- Agent 可能先访问空 account，再尝试另一连接，增加延迟和错误路径。
- 应明确配置来源、作用域、身份和唯一连接；重启后验证运行进程实际继承的配置。

## 153. 如何保护知识库 Key？

**回答要点**

- 使用环境变量或 Secret Manager；
- 不写入 Prompt、Skill、仓库和 Trace；
- 短期凭证、最小权限和轮换；
- 日志只记录 Key 指纹或配置状态，不打印明文。

## 154. Ultron 小专家的边界是什么？

**回答要点**

- 只回答有可靠知识依据的问题；
- 不擅自修改 Issue、配置或生产系统；
- 不把工具故障伪装成无答案；
- 高风险操作和证据不足问题转人工。

## 155. 你会如何继续优化它？

**回答要点**

- 建立真实评测集和故障注入测试；

- 知识缺口自动归类，但写知识库需人工审核；

# 第十四部分：不能过度声称的内容

面试中要严格区分“用过”“集成过”“设计过”“实现过”和“深入优化过”。

## 可以重点讲

- 多 Agent 研发流程和职责划分；
- Prompt、Skill、MCP 与工具编排；
- 知识检索路由和故障降级；
- Trace 分析与无效调用优化；
- 人工 Gate、证据链和质量治理；
- 真实失败案例。

## 没有实现证据时不要直接声称

- 从零实现向量数据库或 HNSW；
- 训练 Embedding/Reranker/LLM；
- 做过 SFT、PPO、DPO、GRPO；
- 构建万级并发 Agent Runtime；
- 实现 Kubernetes 多租户沙箱；
- 已在线上达到某个成功率或性能指标；
- 所有代码均独立手写。

更稳妥的表达：

> 我在应用层做了检索路由和 OpenViking 集成，理解 Embedding、Rerank 和向量检索原理，但没有从零实现向量索引引擎。
